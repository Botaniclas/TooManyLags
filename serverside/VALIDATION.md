# Beta release validation - 0.13.1

Beta release. Fixes the reproduced pursuit stall after our own guarded mob delegation by retaining its observed idle starting point. Existing combat guards, the optional ability forecast and the disabled solo diagnostic remain. No live multiplayer certification or measured CPU/latency gain is claimed.

All 32 verification groups pass against released Dedicated Simulation 1.23.2, including 162 hostile-mob assertions on both managed runtimes, 151 native metadata checks, the actual Valheim Mono startup contract probe and 45 production BepInEx settings. The declared 1.18.0 minimum also passes separate metadata/startup checks. Evidence and hashes are in verification.json and docs/audits/backend-contracts-0.13.1.json. No live Unity combat or multiplayer session was started.

## Beta package preparation

The install ZIP has seven root entries and the verified DLL, with no bundled game/dependency assemblies. The source ZIP excludes nested audit build directories, binary artifacts and locally extracted external reference code. The separate Wiki ZIP contains exactly three English pages plus an author index: Configuration, Compatibility, and Report bugs and ideas. Config scope, tuning keys, server-only limits and the correct dependency are checked by `validate-release.ps1`; package text, DLL hashes, config layout, CLI metadata and the 256x256 icon are checked before output archiving. Wiki pages are supplied for manual entry; publishing the package does not create them automatically.

## Hostile Mob grid and observed-attack handoffs

### Chasing after our own handoff

The reported 0.13.0 sequence alternates twice, then parks a player-to-server request for repeated status samples with inAttack=False, observedAttack=False and forecast=False. Its first observed attack permits the third transfer; the next server-to-player transfer resets history and repeats the stall. MobOwnerChanged cleared all local attack history, and MobIdle treated alert/target presence as unknown combat before the forecast could run. Native BaseAI.SetTargetInfo reports target presence throughout pursuit; it does not report an attack or a successful hit.

A regression reproduces the failed return after our idle delegation before the fix. A single loaded-mob IdleHandoffObserved bit now retains the idle starting point only after our own successfully checked player grant. It is cleared by native owner/revision changes, a recognised new attack trigger or an observed attack animation. It only excludes that known handoff from the no-history branch; actual attack, startup, loop, stagger, charge, quiet observation, forecast, final owner/revision and loaded-area checks are unchanged. External/late-loaded histories are not promoted. Guarded player-to-player transfers preserve the same continuity. There are no new timers, scans, packets, cooldown assumptions or steady physics jobs; work that was incorrectly blocked can now reach the existing forecast when a transfer is genuinely pending.

Eight regression assertions cover pursuit without a first attack, external reassignment, new looping/unseen/triggerless attacks, retained forecast veto and movement wake, and guarded player-to-player continuity. These complement the original tests; live re-testing of the reported sequence remains required. Test logging adds cached armed/combat/idle-handoff flags only when the existing diagnostic emits a status sample.

### Solo diagnostic

`EnableMobOwnershipTest=false` leaves no test selection scan, timer or test log. When explicitly enabled, the existing grid check selects one nearest eligible, grid-covered Hostile Mob within 20 metres of the only accepted player. The override supplies only that node's desired owner to the normal ApplyMob path; startup/attack/loop/stagger/charge guards, optional forecast, ownership revisions, area readiness and normal targeted snapshots remain in place. Successful writes, not elapsed time, allow a reverse request after MobOwnershipTestIntervalSeconds (default one second). Pending requests are not cancelled or flipped to manufacture apparent successes. Normal grid activity cannot undo the selected test target between requests. Actual addon commits are counted separately from external owner assignments.

The mode stops on death, unload, disconnect, loss of eligible state, more than 64 metres of separation, a second accepted player, unexpected ownership or five minutes. Manual server command tml_mob_test_stop stays stopped across controller recreation for that plugin session. Stopping discards the override and queues normal policy; it forces no owner reset and preserves observed attack history. Only explicit test activity creates diagnostic strings/logs. Fixtures cover the disabled path, one-node selection, both guarded directions, held targets, a prolonged actual attack, completion without reissuing, real forecast veto, stop/cleanup paths and continued normal ownership of other mobs. A solo test cannot certify simultaneous multiplayer input or delayed transport behavior; command registration itself is compiled against the installed game but not driven through a live server console in these fixtures.

### Additional ability forecast

`EnableMobAttackForecast=true` observes existing source-owner native attack triggers even when no transfer is pending. Profiles are cached by prefab; a loaded mob allocates one deadline array on its first uniquely recognised weapon use. Primary/secondary/random/chain variants share that weapon's cooldown; the native unarmed fallback is included. Ambiguous names do not mark multiple possible weapons as cooling and cannot weaken an existing looping-attack guard. Unobserved alternatives, unavailable RTT, changed owner revisions, backwards clocks and unsupported metadata cannot manufacture a remaining safe interval.

Deadlines use native game time and subtract 100 ms plus a cached full source RTT. This is deliberately earlier than the received signal's apparent cooldown and remains an estimate, not a packet-age bound. Private global recovery timers are not reproduced. A true server-owned source uses its existing actual Attack completion path without this speculative veto.

Only actual player-source transfers after the existing attack/startup/loop/stagger/charge/idle guards can reach the forecast. If all modelled abilities are cooling, there is no geometry query. Otherwise players are checked first through existing scene identities. A matching player avoids both the native character-list sweep and all physics work. Other creatures use the reused native Character.GetAllCharacters list: their native AI radius can exceed physical collider bounds, so a collider sphere cannot safely exclude them. A cheap squared-distance gate precedes faction and per-ability angle work. Only attackable static targets need the reused 128-collider nonallocating physics query; saturation remains uncertain. Native target radius is included; reach grows by 0.5 metres and horizontal half-angle by 5 degrees. Inverted-angle checks expand their allowed side. Static reach uses closest surfaces and facing uses the native centre. Native minimum range constrains weapon selection, not every subsequent attack, so it cannot prove an equipped weapon unusable.

A positive forecast is cached and parks only that mob. It creates no repeated 20-ms physics work; the existing short timer remains for actual attack observations. Its own movement/turn and relevant nearby movement, native alive/dead/tame/hostility transitions, load/unload or new ability events invalidate it. A changed pose wakes the pending decision directly, without another grid interval; if no ready attack still fits, the original owner/revision/readiness checks can commit. Mere movement cannot bypass a running attack or prove a gap while a ready attack still fits. Mob turning uses a direct waiting-node lookup rather than a sweep; target-only turns affect no attack geometry and do not wake other mobs. Direct scene-instance lookup supplies target radius for cheap spatial wake filtering; teleport checks use old and new positions. Far actor movement and unrelated player samples cannot defeat the blocked-result cache. Native Deserialize bypasses rotation setters, so an optional receive snapshot covers that path. Unchanged imports and nonfatal damage do not repeat the geometry query. Missing scene bounds use conservative invalidation; incomplete native capsules block the affected prediction rather than shutting down the whole addon.

No extra ability network messages, duplicate AI, pathfinding or line-of-sight raycasts are introduced. Collider references and temporary target sets are cleared after each query; waiting nodes leave all indexes on unload/release/last-peer departure. Only prefab metadata remains world-cached. Actor bounds and native broad-phase geometry can still lag authoritative remote state. A padded local query cannot prove what the owner is about to do, and this model can hold an owner longer during combat. Disabling the option preserves the original attack guards without forecast observation arrays or queries.

The native startup probe checks actual observer state types without detouring Unity-initialised classes in a standalone host. Attempting native Animator detours there needs Unity internal calls unavailable outside the engine. Harmony observer detours run in the controlled fixtures on both runtimes; actual Unity scene and transport validation remain separate.

`HostileMobs=true` enables eligible untamed native MonsterAI/Humanoid creatures. Actual native tame state selects the independently enabled tamed-animal category; friendly Players-faction summons, custom AI subclasses and unsupported interaction roots remain excluded. Default ownership still comes from Dedicated Simulation; the cold backend route cannot bypass the live first-delegation attack gate.

Only a shared mature grid field invokes the 90-degree 3D cone selection. Normal mobs use 8 metres; native Character.IsBoss selects the independent 10-metre boss default. With ServerOwnedWhenMultiplePlayersInMobCone=true, one eligible living, ready player wins; zero or multiple candidates select the server. Counting cannot prune candidates farther than the current nearest player, and exits on the second eligible candidate. Disabling that option retains nearest-player pruning and selection; exact distance ties prefer the eligible current owner, then a deterministic UID. Shared mob poses and changed player samples invalidate the small cached decision; pending guard checks do not repeat unchanged cone searches. Selection is revalidated at the actual commit, and native area readiness is checked only once the attack guard permits a server takeover. Exclusive grid fields retain their own player decision without invoking the cone.

Source-server permission checks actual current Attack completion, InAttack, stagger and charging. Source-client permission is observational: recognized native animation triggers, a seen attack phase and at least one idle observation step. Trigger startup gets a bounded observation period; failing to see entry parks the work rather than forcing a transition. Unknown active history and uncompleted loops are parked until native evidence. Owner/revision changes invalidate old observations. No private combat fields are written, no attack-end acknowledgement is invented, and exact client cooldown state is not transferred.

Only pending handoffs use the 0.02-second due queue. Unload, native release, category changes and the last player's departure cancel it. Real updated owner snapshots are sent to both involved player peers, using Valheim's native data envelope. Owner-directed damage, alert, heal, noise and tame requests retain original sender/payload routing. No client protocol, new dependency or per-physics poll of all loaded creatures is added.

Managed production fixtures cover initial delegation, cone geometry/range/height/ties/dead players, same-cell player motion, mob turning, stale selection, private unfinished server Attack, startup gaps, immediate next attacks, loops, unknown history, owner revisions, inactive/disabled categories, native tame transitions and cleanup. New cases cover multiple candidates in either enumeration order, farther second candidates, eligibility filters, exclusive fields, commit-time recount after an attack, native boss detection, exact 10-metre inclusion and independent boss overrides. Stable solo/shared fixtures assert no repeated attack/cone work or owner writes. Installed-native metadata and actual Valheim Mono startup checks verify the private Attack reader, native trigger signature and IsBoss/m_boss contract. These checks do not exercise Unity animation scheduling or real network combat. Remote attack-start races, headless playback, private cooldown migration and other mods remain live-test boundaries.

## Native cart grid and hitch priority

The catalog now accepts exact native Vagon roots with one shared public Container and matching Vagon.m_container / Container.m_wagon links. The latter is necessary: native RequestOpen must actually call the source's Vagon.InUse, not merely check inventory use. Custom/multiple/private cargo identities and unsupported controls stay native. Cart and inventory share one owner; cargo handlers and actual hitch grants are not replaced.

A read-only inspection of the installed game's actual Cart prefab confirms both serialized cart/storage back-links, public cargo and its persistent, nondistant network override on the same root. Evidence: `docs/audits/cart-prefab-contract-0.9.0.json`. This asset check does not start Unity or exercise live physics.

Idle carts use the existing mobile-cell index. Attached carts leave the grid until an observed native Boolean detach event; the Boolean s_attachJointHash must not be confused with ZSyncTransform's string at that hash. Current local Vagon.InUse, the replicated Boolean joint and cargo-use flag veto automatic handoffs. Available client sources always use the native RequestOpen commit/receipt path, even outside player coverage. A server/intermediate server physics takeover requires native area readiness.

An RPC_RequestOwn grant can precede the client's Update/CanAttach, so routed remote hitch requests reuse the existing per-loaded-object coverage-contribution map. They block automatic handoffs without removing the idle cart's index. Observed attachment retires that owner's pending request and lets the actual joint protect use; native RPC_RequestDenied clears only its addressed requester. Departure, rapid re-entry and moving cells use the existing contribution timestamp instead of a guessed completion timeout. Unknown failed local CanAttach completion conservatively keeps that remote requester protected until departure. Actual source-local pending hitch starts on an already-owning vanilla client are invisible before its Update, so the short native pre-attachment window is not an acknowledged lock. The source's real joint/inventory checks remain active.

No cart timer, per-physics object scan, extra client message or competing backend owner writer is added. Requests allocate storage only when received, use the existing coverage start and are released with the loaded node. Shared item/cart request-helper extraction preserves the existing item behavior and its regression checks. A blocked ordinary cart handoff waits for fresh relevant activity, observed detach, or native denial. This is separate from boats' explicitly requested existing-timer overlap retry. Live pulling, concurrent cargo use, bad attachment positions, disconnect/teleport and multiplayer physics still need a world-copy test.

## Boat grid and native cargo protection

Native ships/rafts with known controls are classified separately from stationary chests. One shared, public native cargo identity is supported; independent/multiple/private inventories and unknown actions remain native. Boats use a cached local helm offset transformed by current native position/rotation. Native position, rotation and receive events reindex only a changed helm cell; the server loaded-area cache still uses the hull's actual zone. Steering-user state does not veto a grid handoff; cargo in-use state does.

Cargo reuses the existing native RequestOpen source commit and matching response/revision receipt, rather than inventing a second inventory protocol. Unlike stationary chests, even an empty helm cell still requires the available source's native cargo check: a long ship's cargo can be used away from its helm. Server/local in-use state and mobile loaded-area readiness veto takeovers. Moving players/boats produce normal field updates. An explicitly requested exception retries only blocked, genuinely overlapping server decisions on the existing native two-second boat timer. Settled, solo and vacant boats get no timer-driven inventory query or new scheduler. Visible in-use state still vetoes the attempt before any remote query. Native cargo opening retains its whole-boat ownership grant. There is no independent inventory owner or new client installation requirement.

The released backend's active Ship.UpdateOwner prefix is intercepted only for managed ships, and its helm-response SetOwner call is filtered only for the same indexed identities. Disabled, unloaded, released and unsupported boats retain dependency policy. Native helm requests, grants and steering handlers remain; stale owner-directed steering/opening requests reuse existing ordered native snapshot routing. Actual server ownership transitions retain the dependency's local water-impact timestamp grace. No extra ship update loop or distance scan is added. The existing backend timer retains a constant-time identity filter and can queue the above blocked-overlap retry; the native rotation setter has a ship-only reindex filter with an immediate zero-ship exit.

Controlled fixtures exercise solo/shared ownership, steering-active transfers, cargo refusal/grants/receipt, return after departure, outside-helm cargo protection, unloaded physics, helm offset/rotation/movement, stale steering routing, stationary zero repeated object work, backend noncompetition, disabled ships and rollback. Installed native/released-backend metadata and startup binding checks validate the used contracts. Live sailing with two vanilla clients, opening cargo during overlap changes, boarding/disembarking, high latency and wave-impact behavior remains required.

## Loose-item pickup protection and departure

The old controller pinned every ItemDrop after any player assignment, at initial registration with a player owner, and at any native pickup request. It then removed the object from grid buckets until unload, so an unsuccessful pickup could never release that policy. Version 0.7.1 keeps loose items indexed. A nearby client owner is retained because ItemDrop/Humanoid pickup may run locally without a server-visible request or completion. Actual native requesters are tracked only for their current coverage contribution; its existing start timestamp distinguishes re-entry from uninterrupted coverage. No new field clock, global historical cache, object distance test or periodic pickup poll is introduced.

Requests are pruned only on actual object/field work or another native request. Moving items rebind surviving protection to their current cell. Departed, teleported or disconnected owners/requesters no longer install a lifetime pin; configured exit retention, native zero-owner releases, source-update cancellation and mobile loaded-area checks remain active. A disconnected/out-of-area item owner does not require an unavailable RTT sample. Live fish and actual fishing hooks retain their previous policy. Native pickup callbacks and item contents are not replaced; a failed private client pickup is not claimed to be directly observable.

## Automatic chest grid ownership

The previous policy explicitly dropped player-directed container decisions, so chests could acquire a player owner only through real native opening. Version 0.7.0 delegates idle server-owned public stationary chests to a sole grid player. Different available player owners are checked by the existing native RequestOpen transaction to the headless server; matching reply and owner-revision receipt complete that transaction. As before, after an expired reply window an exact completed server receipt can use the current idle server-owned contract on fresh activity; timeout alone neither changes ownership nor retries. Pending and half-imported receipts cannot be certified by the ordinary same-owner shortcut. No fake opening response is sent to a player, no inventory contents are rewritten, and only actual player grants schedule a native targeted ZDO send.

An initially unowned chest can use a mature grid decision in the backend assignment hook. Existing owners stay on the guarded live-node path. Stale native opening requests use the existing ordered one-object routing; native stack/take-all transactions and replies are not redirected. Tests cover refusal, both grant/receipt orders, partial imports, deferred retry, native root identities, stationary cost and exit rules. A live world-copy test with two vanilla clients, an open inventory and concurrent real opening is still required.

## Runtime shutdown regression

The actual 0.6.2 server log identifies the next failure exactly: `ZSteamSocket.GetConnectionQuality` enters `SteamNetworkingSockets.GetConnectionRealTimeStatus`, whose client availability check throws "Steamworks is not initialized." Controller.Ping propagated it through LargeGrid and Tick into the plugin's global shutdown path. The diagnostic reports consequently showed `enabled=False; hooks=False; controller=False`, rather than a silent field decision error.

0.6.3 reproduces that exception with an unavailable-client/available-GameServer socket fixture before the change, then uses the real Steam GameServer status API through the socket's actual native connection handle. A getter is bound once; sampling performs no reflection/boxing. Other socket transports retain their native quality call. Telemetry exceptions and failed status results are cached as unknown for one second, leaving local acquisition active and retaining the previous adaptive size. Existing source-to-server transfers requiring RTT remain vetoed until a real sample and fresh activity are available; neither fake ping nor the native ping-heartbeat age substitutes for RTT. Real Steam API signatures/context and native field binding are checked separately; a new live Steam session is still required for final confirmation.

Previously, 0.6.1 reached ready but no berry/stone transfers were observed. Without the later exception, that message alone could not distinguish empty peer selection, registration, filtering or application. 0.6.2 supplied bounded read-only diagnostics rather than claiming another global fix. Those snapshots remain available in 0.6.3: existing event counters, a constant-time scene count, at most four tracked nodes and six named prefab inspections, without scene scans or inventory polling.

Native metadata additionally shows that `Container.m_rootObjectOverride` is a ZNetView, whereas the old classification fixture incorrectly modeled a GameObject. Comparing the override to the root GameObject wrongly rejected matching non-null overrides. This specific container defect is fixed and covered with the native field type. It does not explain all berry/stone failures.

## Startup regression

The first 0.6.0 live test reported the addon stopping with "Dedicated Simulation's core ownership patch is not active." The released 1.18.0 backend registers each feature under `MVP.Valheim_Serverside_Simulations.<Feature>`, whereas the addon wrongly required the unsuffixed plugin GUID. Replacing the fixture's artificial shared Harmony ID with the real Core/FireControl IDs reproduces that exact exception before the fix. 0.6.1 authenticates the installed Core method and FireControl method's dependency assembly instead of their Harmony labels. Missing/removed patches and a different method registered under the expected label are still rejected. No handoff protection is disabled.

## Runtime and cleanup

- Public stationary chest handoffs create native requests only when taking a different available player's chest within active coverage. Idle server-owned chests delegate without a query; empty fields return directly. Real opening remains native, without a synthetic player-directed request. Refusal/timeout never forces a write or retries on a clock. Fresh field activity can retry after backoff; late first activity does not add another artificial timeout delay. Completed/unused requests are bounded by loaded objects and cleared on unload/world reset.
- The inventory bridge preserves native protection rather than adding a client-side acknowledgement. Native pre-inUse GUI timing, modified interaction distances, remote private transactions and other mods' custom inventory actions remain outside its guarantee. Private/custom/deferred inventories and mobile inventories other than supported boat cargo stay native.
- Default player sampling remains 0.1 seconds; unchanged cell/heading/fast-speed coverage does not enumerate object buckets. Velocity is read only where a nonzero forward timer can be accelerated; no square root or extra packet is needed.
- The full rear red 3x3 is retained in both retention modes. Yellow-off masks request twelve cells with rounded patterns; a speed-only change adjusts the orange tier without changing geometry or restarting request ages.
- At the default 200 ms threshold, directional coverage uses precomputed 16-red/3-orange cardinal or 20-red/3-orange diagonal masks. It shrinks below 75% of the threshold; unknown telemetry retains the active size. Native RTT sampling is cached for one second and reused by protected takeovers. Full-grid mode and disabled adaptation perform no adaptive ping query.
- Observed refill holds use only a timestamp and per-station native state snapshot. Seven actual refill-handler prefix/postfix pairs compare accepted server-side changes; normal client receive events compare fuel, queue, ammo and empty-to-filled cooking slots. Automatic consumption and occupied-slot cooking conversions do not arm the hold. There is no expiry scheduler, station poll or global numeric-ZDO setter hook.
- Pure local controls have no grid bucket. Their default server assignment runs at registration inside an active player area; native region release is retained.
- Fixed static buildings also have no grid bucket. One-time registration/actual ownership-change jobs use the existing scheduler. The optional static grid is off by default.
- Native position and state events update only indexed mobile objects; actual owner changes invalidate only the affected managed object. Events are deduplicated until the next controller pass, after native deserialization finishes. Global setter hooks still add a small filter/lookup cost; they are not free.
- Wild tameable candidates are indexed so a real tame-flag change can activate them without reloading. Riding/following/transport/combat suspend grid control. Native rider grants keep their recipients; an accepted grant is not cleared by another player's denial.
- Loose items stay in grid buckets. A client owner and current native requesters keep priority while covering the item; departure/re-entry uses existing grid contribution state, not a guessed completion timeout. Request storage is per loaded item, pruned on relevant work and bounded by current nearby requesters. Native fish/fishing pins keep their previous unload lifetime.
- Only actual mobile server takeovers check native loaded-area readiness; results are shared by zone within that pass. A blocked object waits for fresh relevant activity rather than repeatedly scanning the area.
- Only actual protected player-to-server attempts allocate pending jobs. A shared indexed heap processes due work; cancellation/unload removes entries immediately.
- Incoming native source data cancels a pending takeover. No fast world poll, physics hook, per-object coroutine, delayed interaction queue or automatic post-cancellation replay is added.
- The rare stale route sends one native object snapshot and the original action through the same peer connection. It does not call a full-region sync scan or forge native peer revision bookkeeping.
- No-player departure clears pending transfer/latency state. Outstanding field-retirement timers drain before the controller becomes idle, avoiding the previous early-return gap. Unloaded instances leave their indexes and wait sets. Remaining backing capacity is a world-lifetime high-water allocation, not a cache of historical fields.

## Compatibility boundaries

Unsupported inventories, signs, portal names, stands, unsupported vehicles/creatures and deferred actions are not proactively rebalanced. Supported public stationary chests, native boats, idle carts and eligible idle tamed animals use the grid; friendly magic summons remain excluded. The addon never opens a player's GUI to query permission and does not infer an editor start from server state. Boss stones and active dependency FireControl sources stay with their existing policy by default. `RespectBackendFireOwnership=false` opts eligible enabled refill/fireplace prefabs into normal grid ownership and excludes only those prefabs from FireControl's takeover pass. Other fires and disabled categories retain their native policy. The same Harmony owner restores native behavior on rollback. Server-only FireControl rules cannot be fully enforced on player-owned sources. Restart after changing dependency feature modes.

No client DLL, custom camera publisher or PUP integration is required. The addon has no FiresGhettoNetworking/fork binary reference; its required backend is bound through installed plugin and active contract discovery. Structural startup checks can disable the addon after incompatible game changes; no hard version-number lock is used.

## Remaining limits

The earlier 0.3.1 door audit reproduced a settled-cache gap after an injected external owner write. This version invalidates only the affected loaded node on an actual `SetOwnerInternal` event; the regression fixture verifies repair without movement and preserves native zero-owner release. Native door animation can still reject input, and no animation-specific guard is added. Headless animation behavior and the earlier user incident are not live-reproduced. See `docs/DOOR-AND-LONG-ACTIONS-REVIEW.md`.

Native `IsAreaReady` checks loaded instances, not client/PUP colliders. Replicated tame/use/combat flags do not acknowledge unseen client actions. The concrete AI target remains owner-local; only target presence is replicated. Riding grants whose completion cannot be observed can remain on the native path until a clear release or unload.

A cancellable RTT window observes only updates received before its deadline. There is no generic old-client cutoff/final-state acknowledgement. Native state-before-request ordering does not prove that an arbitrary recipient has instantiated its scene object; the intended requesting client already interacted with that loaded object. Crossplay and third-party transport/serialization changes need separate validation.

The refill hold starts at server observation, not at an unseen client input. Coalesced consumption/removal and insertion can leave no detectable net increase or occupancy edge. Native source cancellation still applies, but neither mechanism is a universal transaction acknowledgement. Unsupported inventories and deferred actions remain excluded rather than receiving unused or speculative guards; see `docs/NATIVE-ACTION-GUARDS-2026-10-17.md` for the earlier review.

The live index still waits for server instance registration for later grid control of already-owned objects. Initial assignment can use a mature grid decision earlier. Do not confuse successful data ownership with a loaded collider or a complete scene.
